DevDual

System Overview

Real-time competitive coding platform with auction-based problem allocation

Problem Statement
  • Traditional contests test pure algorithms in isolation, lacking strategic depth.
  • DevDual introduces resource constraints bringing an economic twist.
  • Transforms coding into a high-stakes game where risk vs reward matters.
Core Mechanic
  • 2-person teams split into a Bidder vs Coder.
  • Bidder competes in a real-time auction with a fixed virtual purse.
  • Wins deplete currency instantly; points rely solely on Coder's success.
Strategy
  • Unused currency holds no value — teams must spend strategically.
  • Coordination between the Bidder's budget and Coder's skill is the key to winning.

Engineering

Key Engineering Systems

DevDual broken down by subsystem — what each does, why it's non-trivial, and what tradeoffs were made.

// Real-Time System Design

Native FastAPI WebSockets. No Redis pub/sub, no external broker — direct in-memory connection management. Works for single-instance deployment; horizontal scaling requires shared state.

ConnectionManager
In-memory dict: auction_id → list[WebSocket]. On connect: add to room. On disconnect: remove from room. Bid broadcasts iterate the list.
Bid Event Flow
Client sends bid via HTTP POST — not WebSocket. Validated + locked in DB → result broadcast to all WS connections in that room.
State on Reconnect
On WS connect, server sends current auction snapshot from Redis (problem_id, current_bid, winner, time_remaining) before entering live stream.
Authentication
JWT passed as query param on WS connect. Validated before connection accepted. Invalid token → connection rejected immediately.
// Caching & State Strategy

Redis is used for six distinct purposes — none of them are 'just caching for speed'. Each use case solves a correctness or operational problem that a relational DB is wrong for.

Use CaseStructureTTLWhy Redis — not DB
OTP StorageString — key: user:otp:{email}5 minutesOTPs are ephemeral. DB storage requires a cleanup cron. Redis TTL handles expiry natively.
JWT BlacklistSet — value: token hashMatches token expiryStateless JWT cannot be invalidated on logout. Redis provides revocation store checked on every request.
OAuth StateString — key: oauth:state:{id}10 minutesOAuth state prevents CSRF. Must be temporary and not persist to DB.
Team InvitesString — key: invite:{code}24 hoursInvites expire without a cleanup job. Redis TTL eliminates need for cron.
Auction StateHash — auction:{id}:stateAuction durationFast reads for WebSocket broadcast and reconnect sync. DB query per broadcast would spike.
